一、前端两层过滤逻辑（落地标准做法）
1. 先识别代码特征，直接剥离
前端 JS 判断选中内容里的代码标记，匹配这些特征直接剔除 / 单独隔离：
代码标签：<code> <pre> <samp> 内部全部内容；
代码行特征：包含 //注释、/* */、= {} () [] ;、变量、函数名、接口地址、JSON 片段；
行格式：以 $ > # 开头命令行代码、连续数字 + 符号代码串；
markdown 标记：``` 代码块、单行代码。
处理规则二选一：
直接删除：纯翻译场景，代码无翻译意义，过滤后只传自然文本给 AI；
占位符替换（推荐，体验更好）：把代码替换成 {{code_01}} 这种占位符发给 AI 翻译，AI 不会翻译占位符；翻译完成后前端再把原始代码回填到对应位置。
2. 区分场景，控制过滤强度
场景 A：划词翻译（用户手动选中一段文字翻译）
选中内容里检测到代码片段 → 占位符替换；
仅把干净自然文本 + 占位符传给翻译模型；
AI 只翻译人类可读文字，代码占位符原样返回；
前端拿到译文后，回填原始代码，输出完整带代码的译文。
示例：
原选中文本：调用fetch('/api/list') 获取列表
前端替换：调用{{code_01}} 获取列表
发给 AI 翻译，翻译完再把 {{code_01}} 换回 fetch('/api/list')。
场景 B：整页批量翻译网页
遍历所有 DOM 文本节点，<pre><code> 直接跳过不提取；普通文本内内嵌代码用占位符隔离，不删除，保证页面结构不乱。
二、为什么不能把代码直接丢给翻译 AI？
翻译效果崩坏
模型会尝试翻译变量名、接口路径、函数关键字，比如把 getUserInfo 翻译成 “获取用户信息”，代码完全失效；
浪费 token
大段代码字符极多，无翻译价值，白白增加计费；
歧义干扰
符号、特殊字符打乱模型上下文，普通文字翻译容易出错。
三、和你现有架构结合的优势
过滤全部在前端本地执行，不需要调用 AI 识别代码，零额外开销；
和你现有的 DOM 清洗、文本提取逻辑复用同一套节点过滤工具函数，不用重复开发；
划词翻译是独立轻量链路，过滤后报文极小，不会像网页操控那样产生十几 KB 数据；
配合 OCR 识图翻译：截图里的代码，OCR 识别后同样正则过滤代码符号，再送入翻译模型。
四、边界兜底：用户明确要求翻译代码注释
如果用户指令里明确说明 “把这段代码注释翻译一下”，意图层识别到特殊需求：
前端不再过滤注释，仅过滤函数 / 变量代码，单独提取注释文本送去翻译，代码本体保留不变。
极简总结
过滤动作全部由前端完成，不会原样把代码传给 AI；
主流实现：代码替换成占位符，译文回填；极简方案直接删除代码片段；
好处：避免代码被错误翻译、节省 token、提升翻译准确度。
代码都是 pre 和 code 吗？
不是只有 <pre> + <code>，网页里代码载体分三类，前端过滤要全覆盖：
1. 标准规范代码块（最常见）
块级多行代码：<pre><code>...</code></pre>
行内小段代码：<code>fetch()</code>（无 pre，只单行）
2. 第三方代码高亮容器（掘金、CSDN、GitBook、MD 文档站）
网站自定义 class 容器，没有 pre/code：
html
预览
<div class="hljs">
  <span class="token-function">getUser</span>
</div>
<div class="language-js">...</div>

特征 class：hljs、language-xxx、code-block、highlight、syntax
3. 纯文本展示代码（后台、接口文档、命令行）
只用普通 div/p，靠样式等宽字体展示代码，无专用标签：
命令行：$ npm install、> curl xxx
JSON、接口返回文本、日志文本
这类没有任何代码标签，只能靠文本内容正则识别：
包含 { } [ ] ; = // /* */ 、函数名、路径、端口号等特征串。
前端完整过滤方案（适配你的划词翻译）
标签黑名单直接跳过提取文本
pre, code, samp
class 特征黑名单跳过
匹配包含 hljs / language- / code-block / highlight 的元素
兜底正则过滤（选中文本后）
对提取到的文字做正则，识别代码片段，替换为占位符，防止漏网的无标签代码。
实操建议
只靠 pre/code 会大量漏过滤，出现代码被翻译乱掉；
三层组合（标签 + class + 文本正则）才能完整拦截所有代码。
